# Лабораторная работа № 1 - интерфейсы и архитектура

## 1. Цель

Спроектировать устойчивые границы учебной базы данных MiniKV до реализации
хранения и сетевого взаимодействия. Публичные операции должны остаться
неизменными на следующих этапах: `put`, `get`, `delete` и `list_keys`.

## 2. Что реализовано

- создан импортируемый проект для Python 3.12 с `src`-структурой;
- определены интерфейсы публичного хранилища, физического движка, репликации и
  маршрутизации по сегментам;
- добавлены JSON-совместимый тип, структуры изменения и сегмента;
- определены предметные ошибки отсутствующего ключа, сбоя сохранения и
  недоступного узла;
- добавлены заглушки, которые явно завершаются `NotImplementedError`;
- подготовлены контрактные тесты без ожидания рабочей базы данных.

## 3. Архитектура

Клиент зависит от `IKeyValueStore`, а реализация хранилища зависит от
`IStorageEngine`. Обратной зависимости нет. `IReplicationManager` и
`IShardRouter` определяют будущие границы, но не содержат транспорта, алгоритма
SHA-256 или сетевых деталей. Полная UML-диаграмма находится в
[diagrams/lab1_components.md](diagrams/lab1_components.md).

## 4. Как запустить

Для проверки контрактов из корня проекта используется команда:

```bash
uv run pytest tests/test_interfaces.py
```

Команда требует установленного в проектном окружении `pytest`. Зависимости не
добавляются автоматически.

## 5. Как проверено

Контрактные тесты проверяют абстрактность интерфейсов, наличие и сигнатуры
методов, наследование предметных ошибок, валидацию пустого ключа и явный отказ
заглушек. В текущей рабочей сессии тесты не запускались, поскольку для этого
требуется отдельное разрешение пользователя; фактический вывод следует добавить
в отчёт после запуска указанной команды.

## 6. Вывод

Подготовлена архитектурная основа MiniKV с направленными зависимостями и
фиксированными публичными операциями. Физическое хранение, REST API, репликация
и алгоритм шардинга намеренно не реализованы и относятся к лабораторным работам
№ 2–5.
